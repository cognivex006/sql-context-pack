# 3.5.3 — release and migration notes

## Why a patch version

It fixes the owner-reported slowness and adds no surface. The MCP tools, HTTP routes, CLI,
managed header, output format `2` and every response field are unchanged, and bundles are
byte-identical to 3.5.2 for the same source. Requirement [v1.8](../spec/design-spec-v1.8.md)
records it as phase 1 of the 4.0.0 track.

## What changes

- **Connections.** Read metadata statements reuse one connection per worker thread instead of
  one per statement. Each statement keeps its own read-only transaction.
- **Concurrent analysis.** A catalog analyzes objects on at most four concurrent read sessions.
  A refused session is handled exactly as a refused connection was in 3.5.2; on SQL Server it
  is a per-object analysis failure. A login capped below four concurrent sessions can therefore
  see failures it did not see before.
- **SQLFluff workers.** Formatting runs in up to four long-lived worker processes (two on a
  machine with four or fewer logical processors) on the configured host Python. Each holds one
  interpreter with SQLFluff loaded. They are recycled after 2,000 commands and stop with the
  service.
- **Ordered output.** Formatting runs concurrently, but files, progress and accounting are
  written in catalog order.

## What to expect

The largest gain is formatting, which no longer starts an interpreter three times per object.
Database-side gains grow with network latency to the source server. Run the same export before
and after the update to see the difference on your own data; a retained catalog from 3.5.2 is
reused unchanged.

## Migration

None. Update with `sqlctx doctor update --host <host> --version 3.5.3`, or the one-line update,
then confirm package, plugin and service versions all report 3.5.3 with
`sqlctx doctor check --host <host>`. The service must restart to load the new code; the update
does this.
