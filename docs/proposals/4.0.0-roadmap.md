# Proposal: road to 4.0.0 — one command, one job, one result

Status: **draft for owner review**, 2026-11-07. Not yet a requirement version; each phase becomes
one when the owner asks for it to be built (AGENTS.md §7).

## Objective

The owner asks for SQL context once and gets complete, formatted, verified files, without the
agent looping through twenty tool calls, approvals for read-only work, or questions it could
have answered itself. Security stays enforced in code: credentials never cross MCP, sensitive
values are protected before any result is returned, and only real writes need approval.

## Phase 1b — finish the 3.5.x fixes (patches, no new surface)

Each item is a separate `hotfix/*`, tested on `agrimap-dev`, released on its own.

1. **Geometry and geography samples.** pyodbc cannot read SQL Server type `-151`; 8 tables lose
   their samples. Select those columns as `.STAsText()` (protected like any column) or mark
   them unsupported in the sample, never fail the whole sample.
2. **`doctor` sees a Claude Code plugin from its native marketplace.** Read Claude's own plugin
   registry so package, plugin and service can all be verified; today it reports
   `PLUGIN_VERSION_UNVERIFIED`.
3. **`doctor update` without provenance.** On a machine set up through a native marketplace,
   fall back to the verified release bundle (what the one-line updater does) instead of stopping
   with `UPDATE_SOURCE_REQUIRED`.
4. **`sqlctx service status` on Windows.** It reports `not_running` while the service answers
   health checks; read the SCM and health probe the same way `doctor` does.

## Phase 2 — 3.6.0: one server-side job (minor: adds tools, removes nothing)

Requirement v1.9. Old tools keep working.

1. **`sqlctx_pull`.** One call takes profile, scope (all, or names and patterns) and a
   registered output folder ID. The service runs discovery, analysis, classification,
   materialization, formatting, validation, assembly into the folder and the inventory index
   sync as one job.
2. **Preflight in one answer.** Before starting, `pull` checks profile, scope, folder,
   SQLFluff, write scope and service readiness together and returns every blocker at once, each
   with one exact remedy command. No partial start, no question loop.
3. **`sqlctx_wait`.** Long-polls a job for up to about 50 s and returns phase, counts and the
   current object, so a large job never trips the client's 30-minute tool timeout. Today
   `create_catalog` runs the whole analysis inside one request.
4. **Server-owned bookkeeping.** Idempotency keys are derived from the request; the actor ID is
   set once in owner config; sync batching, cursors and resume fingerprints stay inside the
   service.
5. **One report.** Counts for discovered, analyzed, failed, formatted, parse-failed, skipped and
   unresolved, plus index inserted, updated and preserved, in the final job status. Full lists
   are written as files in the output folder rather than paged over MCP.
6. **Acceptance.** On `agrimap-dev`, "pull all of `agrimap_app` into folder X" completes with at
   most three agent tool calls and no owner question, and the folder passes
   `sqlctx validate output`.

## Phase 3 — 4.0.0: smaller surface (major: removes tools)

Requirement v2.0.

1. **About eight tools:** `status`, `connect`, `pull`, `wait`/`cancel`, `query`, `index_list`,
   `deploy_plan`, `deploy_apply`. The catalog, preview, selection, sitemap, classification
   request/proposal, export batch and fetch/assemble tools are removed from MCP. Their CLI
   equivalents stay for the owner.
2. **Skill rewrite.** `SKILL.md` becomes one decision table of about 60 lines; the 20-step
   workflow reference goes.
3. **Approvals only for writes.** Routine deploy, owner-mode index changes and in-place file
   overwrite keep single-use approval. Read paths need none, as today in practice.
4. **Compatibility.** Output format and managed header stay at 2, so existing files keep
   working. `docs/releases/4.0.0.md` maps every removed tool to its replacement.

## How it runs unattended

Each phase follows the same loop: branch from the release tag, build, test (`dev-check`, then a
real run on `agrimap-dev`), merge with `--no-ff`, tag, release with installer assets, update
this machine and verify all three versions.

| Step | Can the agent do it alone? |
|---|---|
| Code, tests, docs, versions, merge to local `main` | yes |
| Read-only runs on `agrimap-dev` | yes |
| Tag, push tag, GitHub release, installer assets | yes, if the owner pre-approves releases |
| Push `main` | **no**: a project hook blocks it; the owner pushes |
| Update this machine's service | needs one UAC approval per update |
| Phase 3 tool removals | needs the owner to approve the removal list once |

Estimated effort: phase 1b about one session; phase 2 two to three sessions; phase 3 one to two
sessions. Each phase lands and is usable on its own, so stopping between phases leaves a
working release.
